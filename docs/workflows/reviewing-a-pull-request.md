# Workflow: Reviewing a Pull Request

There is no CI in this repo (`.github/` doesn't exist) and no existing test suite to lean on — review has to do more work than "check CI is green."

1. **Scope check**: does the diff match the stated intent? Flag unrelated refactoring, especially "drive-by" changes to a stub service's structure that weren't asked for.
2. **Convention check against [ENGINEERING_RULES.md](../../ENGINEERING_RULES.md)**: centralized query constants (not inline SQL), `AppError` subclasses (not bare `Error`), zod validation on new routes, parameterized SQL always. Flag any new inline SQL or bare `throw new Error(...)` in a route/service file.
3. **Contract check**: if an HTTP route or Kafka event payload shape changed, confirm every consumer was updated — grep the frontend (`frontend/src/lib/api/`) and every other backend service's consumers for the changed topic/route. There's no compiler or contract test that catches a missed consumer here; this is a manual review responsibility specific to this codebase.
4. **Deployment-gap check** (per [ADR 0002](../decisions/0002-partial-service-implementation.md)): if the PR adds meaningful functionality to one of the 5 non-deployable services (`media-service`, `group-service`, `expense-service`, `notification-service`, `call-history-service`), does it also add the Dockerfile/compose entry/k8s manifest, or at least call out explicitly that it's deferred? Don't let the gap between services silently widen.
5. **Error-handling check**: does every new Kafka consumer handler catch its own downstream failures (HTTP calls, email sends, etc.)? `notification-service`'s uncaught-SMTP-failure-causes-infinite-retry bug (see [ENGINEERING_RULES.md](../../ENGINEERING_RULES.md)) is exactly the shape of bug to catch here.
6. **Test check**: does the PR add a test for the behavior it changes, even if it's the first test in that file/service? Given zero existing coverage, "no tests, matches existing pattern" is not an acceptable justification here — see [TESTING.md](../../TESTING.md).
7. **Security check** against [SECURITY.md](../../SECURITY.md): any new route exposing another user's data without a narrow response shape (the `GET /:userId` email-leak pattern to avoid repeating)? Any new hardcoded secret fallback? Any new unauthenticated route on a service that should have `authPlugin`?
8. **Docs check**: does the PR update the relevant `AGENTS.md`/`MODULES.md`/contract doc in the same change? Run `node scripts/validate-docs.mjs` on the branch.
9. **Verification claim check**: does the PR description state what was actually run/verified (manual exercise, specific commands), rather than implying "tests pass" when none exist for the touched area? Push back on vague completion claims — see [TESTING.md](../../TESTING.md) for why this matters more here than in a repo with real CI.
