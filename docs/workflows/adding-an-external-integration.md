# Workflow: Adding an External Integration

E.g. a real S3 client for avatar uploads, a push-notification provider, a TURN server. This repo already has two "integration exists in config but was never wired up" examples (S3 in `user-service`, TURN in `call-signaling-service`) — don't add a third.

1. **Add the env vars to `.env.example` and `backend/docs/environment.md` first**, following the existing table format, with a clear default/placeholder and a note on what's required vs. optional.
2. **Construct the client where the service boots** (`src/server.ts` or `src/index.ts`), following the existing pattern: a `create*Client(serviceName)`-style factory in `@nexus/shared` if the integration is reusable across services (like `createPostgresClient`/`createRedisClient`/`createKafkaClient`), or service-local config if it's genuinely one-service-only.
3. **Decorate the Fastify instance** with the client (`fastify.decorate('s3', client)`) so routes can access it via `request.server.s3` — matches how `postgres`/`redis`/`kafka` are already exposed.
4. **Fail loudly if required config is missing**, rather than silently constructing a client that will fail on first use. `user-service`'s `STORAGE_*` vars being read-but-unused (no client ever constructed) is exactly the failure mode to avoid — if the env vars exist, something should either use them or the route should be absent/return a clear "not configured" error, not a fake success response.
5. **Wrap every call to the external system in a try/catch that maps failures to an `AppError` subclass** (see [ENGINEERING_RULES.md](../../ENGINEERING_RULES.md)) — don't let a third-party SDK's raw error reach the client, and don't let an uncaught failure inside a Kafka consumer handler create an infinite-retry loop (see `notification-service`'s SMTP bug in [ENGINEERING_RULES.md](../../ENGINEERING_RULES.md#concurrency-retries-idempotency--proposed-improvement-area) for exactly what this looks like when done wrong).
6. **Update [INFRASTRUCTURE.md](../../INFRASTRUCTURE.md)** with the new external dependency (what it's for, which services use it, what happens if it's unreachable) and the affected service's `AGENTS.md`.
7. **Add a health check** if the integration is load-bearing for that service's core function, following the `healthCheck()` pattern already on `PostgresClient`/`RedisClient`/`KafkaClient`.
8. **Write a test that mocks the external client** at the constructor-injection point (every existing client is passed in, not globally imported, which makes this straightforward) — don't skip this because "there's no test pattern to follow elsewhere"; this is a good place to start one.
