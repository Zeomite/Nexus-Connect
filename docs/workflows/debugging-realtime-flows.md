# Workflow: Debugging Chat/Call Real-Time Flows

For anything that "sometimes doesn't arrive" in chat messages, typing indicators, or call signaling — the most architecturally fragile part of this system. Read [ARCHITECTURE.md](../../ARCHITECTURE.md) risk #1 in full before debugging further; most symptoms here trace back to it.

1. **First question: are sender and recipient on the same process?** `WebSocketManager` (chat-service) and `SignalingManager` (call-signaling-service) both hold connection/room state in a plain in-process `Map` — not Redis, despite both writing a copy to Redis. If you're running multiple replicas (or testing with `docker-compose up --scale chat-service=2`), check which replica each socket landed on first.
2. **For chat**, only events also published to Kafka (`message:new`, `message:delivered`, `message:read`, `chat:created`) have a cross-instance path at all — via each replica's own `ChatConsumer` re-pushing through its local `wsManager`. A `typing:start`/`typing:stop` signal is **never** published to Kafka — it is fundamentally single-instance-only today; don't spend time looking for a cross-instance bug in typing indicators, the gap is structural.
3. **For calls**, `CALL_ANSWERED`/`CALL_DECLINED`/`CALL_ENDED` Kafka consumer branches in `call-signaling-service/src/consumers/call.consumer.ts` are empty stubs — a second replica genuinely never learns about these state changes from another replica. Don't assume a retry or timing issue; read the consumer file and confirm the branch is actually empty before concluding otherwise.
4. **Check Redis is actually being read, not just written**, before assuming a Redis-based fix will work: `SessionKeys.userConnections`/`callRoom`/`callParticipants` are written by both services but — as of this harness's review — not subscribed to or read back by anything. If your fix relies on "the data's already in Redis," verify someone actually reads it; today, no one does.
5. **Reproduce with a single replica first.** If the bug reproduces even with one instance, it's not the cross-instance gap — check heartbeat/timeout logic (30s ping / 60s timeout, both services), payload size limits (1MB chat, 64KB signaling — a message over the limit is a different failure mode than a dropped event), or the specific handler for that message type.
6. **Check `wsUrl` generation for call-signaling** if a WebSocket connection never establishes at all (not a delivery issue, a connection issue): `initiate`/`accept` responses hardcode `ws://localhost:<port>` — see [TROUBLESHOOTING.md](../../TROUBLESHOOTING.md).
7. **If you're fixing the cross-instance gap itself** (not just debugging around it): the shape of a real fix is to actually subscribe to the Redis pub/sub channels that are already being published to, and route incoming cross-instance messages through the same local `wsManager.sendToUser`/`sendToChat` path used for same-instance delivery — don't build a second delivery mechanism, extend the existing dead subscription into a live one. Add a test that starts two in-process manager instances sharing a mocked Redis pub/sub to verify the fix, since no multi-instance test harness exists today.
