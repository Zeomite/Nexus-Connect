# Workflow: Modifying the Database Schema

There is **one shared Postgres schema** (`backend/infrastructure/postgres/init.sql`) for all 9 services — there is no per-service migration framework except `auth-service`'s own hand-rolled one, which only tracks its own `users` table.

1. **Identify true ownership first.** Check [MODULES.md](../../MODULES.md)'s "Key tables" column — table ownership is convention, not DB-enforced (no separate schemas/users per service). Confirm no other service reads/writes the table you're changing before assuming it's safe to change alone (e.g. `notification-service` reads `users` directly even though it doesn't own it — a cross-service read that a schema change could silently break).
2. **Edit `infrastructure/postgres/init.sql` directly** for anything that should apply on a fresh local/compose Postgres — this file has no migration history, it's a single bootstrap script. Keep `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX` style consistent with the rest of the file.
3. **If the table is `users` and you're changing something `auth-service`'s migration runner already tracks**, also add a migration entry to `backend/services/auth-service/src/database/migrate.ts` (array of `{name, up, down}`) so a running `auth-service` can pick up the change without re-running `init.sql` from scratch. No other service has an equivalent — don't assume one exists.
4. **Update every query constant that touches the changed table**: `backend/packages/shared/src/database/queries/<domain>.queries.ts`. Grep for the table name across `backend/packages/shared/src` and every service's `src/` — centralization helps here, but a few known deviations exist (e.g. `user-service`'s `PATCH /me` builds SQL inline, outside `UserQueries` — it won't show up in a query-constants grep).
5. **Update the corresponding shared type** in `backend/packages/shared/src/types/<domain>.ts` and any frontend mirror in `frontend/src/lib/api/types.ts` if the column is ever exposed in an API response.
6. **Add an index deliberately, not reflexively** — check existing indexes in `init.sql` first; e.g. `user-service`'s name search uses `ILIKE '%query%'`, which a plain btree index (already present) can't accelerate — if you're optimizing that path, you need a trigram/full-text index, not just "add an index."
7. **There is no test database or migration test harness** — verify schema changes by running against your local docker-compose Postgres and re-exercising the affected routes manually (see [TESTING.md](../../TESTING.md)).
8. Update [MODULES.md](../../MODULES.md)'s table-ownership listing and the affected service's `AGENTS.md` if ownership or shape changed.
